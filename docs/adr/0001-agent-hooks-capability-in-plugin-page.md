# Agent 钩子配置的能力下放到插件设置页

插件的 `settings` 区本来就跑在设置窗的 realm 里（`src/settings/main.ts` 用 `widgetHost.mount(manifest, "settings", box)`），
所以 `gate.rs` 那条"系统级命令只认 label==settings"对插件页面**天然成立**；真正的缺口是 widget 的 ctx 只有 ScopedBus，没有 invoke 通道。
我们决定给 widget 增加一条**只在 `region=="settings"` 时注入**的受控能力 `agent:hooks`（manifest 声明 + 首次同意框），
把「Agent 事件接入」从「宠物设置」分区整体移交给 agent 桥插件页，宿主不再为该插件保留第二份配置入口。

**备选**：① 由宿主在插件页容器里渲染这块 UI（零新权限，但本体长出一块 agent-bridge 专属代码，每加一个 Agent 都要改本体，
与"本体只提供窗口/渲染/运行时"的架构方向相反）；② 设置窗保持现状、插件页只给跳转（最小改动，但配置名义归属和实际归属不一致）。

**后果**：AGENTS.md 里"跨会话生效的系统级开关一律只认设置窗"这条不变量的含义被改写 —— 从此它指的是**设置窗这个 realm**，
而不再是"只有宿主代码能碰"。任何声明 `agent:hooks` 的插件都能改用户其它应用的配置文件，边界靠权限声明与同意框挡，
不是靠窗口身份。同 realm 里插件自行 `import { invoke }` 仍拦不住（这条已知缺口不变，要等 Web Worker 宿主才收口），
所以本次没有让安全边界变硬，只是把既有的软边界用在了一个更重的动作上。

另一条容易看漏的取舍：**「谁在联动哪个 Agent、hook 装没装」这份状态归宿主持久化，不归插件存储**。
配置归属是 UI 层面的（用户在插件页里看和改），但卸载时机有两条路径插件自己碰不到 —— 插件崩溃、宿主退出，
这两条路径上必须仍能把 `--pet-hook` 条目收掉，否则用户的 Agent 配置里长期留着一条指向我们的 hook，
而每次工具调用都在拉起一个已经没人认领的进程。所以插件的 `deactivate()` 只是快速路径，宿主的状态才是事实源。
